🔓 UnlockStore 解锁状态持久化
localStorage: engchain-unlocked（detail.js:96）
存储结构{bizKey_id: {t: timestamp}}
_key(rec)bizKey + "_" + id（如 "material_123"）
mark(rec)写入 {t: Date.now()}，派发engchain-unlock-changed事件
clear(rec)删除单条解锁记录
reset()清除全部解锁记录，派发事件
isUnlocked(rec) 判定逻辑：
1. rec为空 → return false
2. isFree(bizKey) → return true（personnel/publish）
3. 读取记录 rec0 = _read()[key]，不存在 → false
4. days = _ttlDays(bizKey)，days<0（永久）→ true
5. (Date.now() - rec0.t) < days×86400000 → true，否则false
⏰ 解锁有效期 TTL 配置（_ttlDays）
detail.js:106 — 按bizKey差异化有效期
bizKey TTL 说明
talent 人才7 天人才信息时效性强，7天后需重新解锁
trade 建企买卖30 天与保证金冻结期一致，30天未成交全额退还
material/equipment/labor/cooperation永久 (-1)标准供需类，一次解锁永久有效
franchise 资质招商永久 (-1)分级积分解锁，永久有效
agency 中介服务永久 (-1)已登录用户留资后解锁并持久化；游客阻止解锁+登录引导
personnel 企业招聘不适用免费投递类，不走UnlockStore
⚠️ TTL过期后 isUnlocked()=false，但UnlockStore中的记录不会自动删除（只是判定为过期）。下次解锁时 mark() 会覆盖 t 为当前时间。

三、定价策略分析（优点与问题）
定价优点
1. 积分预付费模式：现金流好，用户充值后有消费动力
2. 批量充值折扣：95/90/85折鼓励大额充值，提升客单价
3. 年度会员¥999：相对于按次付费（约¥125/次），8次回本，有吸引力
4. 中介入驻¥29999：高定价匹配高价值客户，筛选优质服务商
5. 免费额度体系：完善的分层免费额度，降低使用门槛，促进转化
定价问题
1. 积分汇率混乱：代码cnyToCreditRate=1.28（1积分=¥1.28），但实际充值价格为¥0.43-1.02/分，汇率严重不一致
2. 信息解锁定价偏低：98积分≈¥42-125/次（取决于充值包），建筑行业高价值信息定价可能偏低
3. trade保证金固定¥5000：不同交易额应分级保证金，小交易额门槛过高
4. 免费额度过多（已优化）：原实名用户每日10条+月度5条=每月305条免费，已调整为每日5条+月度3条=每月153条，降低50%
5. 年度会员权益单一：仅免费解锁+0.5x积分折扣，缺乏差异化权益，续费率可能低
四、获客转化漏斗分析
游客（每日2条+破冰1条免费）→ 注册引导
注册用户（每日3条免费）→ 实名引导
实名用户（每日5条+月度3条=每月153条免费）→ 付费引导
付费用户（积分消费）→ 充值/会员引导
充值用户/年度会员→ 入驻引导

🔴 问题1（严重安全漏洞）：simulatePayUnlock 余额不足时仍能解锁 + 流水与余额不一致
代码位置：detail.js 第3220-3232行
核验结论：确认存在，且比初判更严重。代码执行顺序：①无条件写unlock_sim_pay流水(-rmb) → ②判断available>=rmb才扣balance+写unlock_cny_pay → ③无条件写platform_income流水(+rmb) → ④write(s) → ⑤无条件UnlockStore.mark(rec) → ⑥无条件toast「已扣¥rmb」 → ⑦无条件unlock()。
影响范围：
• 安全漏洞：余额不足时，balance不扣减，但UnlockStore.mark和unlock()仍执行，用户未付费即可解锁内容
• 数据不一致：流水记录unlock_sim_pay(-rmb)和platform_income(+rmb)已写入，但balance未扣减，流水与实际余额不符
• 平台收入虚增：platform_income无条件写入，即使未实际收到钱
• 用户误导：toast显示「已扣¥rmb」，但实际未扣
完整修改建议：
① 余额校验前置：在写任何流水之前判断available>=rmb，不足时直接return false
② 余额不足时：UI.toast「余额不足，请先充值人民币」+ 引导跳转recharge.html，不写流水、不mark、不unlock
③ 余额充足时：按顺序写unlock_sim_pay → 扣balance → 写unlock_cny_pay → 写platform_income → write → mark → toast → unlock
④ 函数应有返回值：成功返回{ok:true}，失败返回{ok:false, reason:'insufficient_balance'}，供调用方处理
🟠 问题2（中等）：用户切换后余额/积分流水全部丢失
代码位置：databus.js 第261-262行（syncUser）+ 第171-172行（login）
核验结论：确认存在。syncUser回写u.balance={balance,frozen,totalIn}（不含logs），u.credits={balance,quota}（不含logs）；login时BalanceStore.write(u.balance)整体覆盖localStorage；makeStore.load()用Object.assign(def,parsed)，parsed不含logs时def.logs=[]生效，导致流水被重置为空数组。
影响范围：
• 用户A的充值/消费流水在切换到用户B后丢失，再切回用户A时也看不到历史流水
• 钱包页流水记录不可信，财务对账困难
• CreditStore积分流水同样丢失
完整修改建议：
① syncUser()回写时包含logs字段（或至少保留最近50条）：u.balance={balance,frozen,totalIn,totalRebate,logs:b.logs.slice(0,50)}
② 或login()时采用合并策略：读取当前Store.logs与u.balance.logs合并去重，而非整体覆盖
③ 长期方案：流水独立存储（如engchain-balance-logs-{userId}），不随用户快照覆盖
🟠 问题3（中等）：FreeQuotaStore 个人合伙人身份判定不一致
代码位置：stores.js 第1437-1438行（FreeQuotaStore._limit）
核验结论：确认存在。deriveIdentity()中personal='partner'表示个人合伙人（未实名未入驻），但FreeQuotaStore._limit()的realnameOk条件为(personal==='verified'||'professional'||'full' || enterprise==='verified'||'resident')，不含'partner'，导致个人合伙人被归为registered档（3条/天）。而freeQuotaInfo()的allow包含'partner'（享有月度免费额度），creditDiscount()中个人合伙人享有0.8x折扣，身份优先级partner>pro>realname。
影响范围：
• 个人合伙人（未实名）每日免费浏览额度仅3条，与注册未实名用户相同
• 但同一身份在月度免费额度（3条/月）、积分折扣（0.8x）、身份优先级上被视为实名及以上
• 身份判定口径不一致，用户体验困惑
完整修改建议：
① 在realnameOk条件中增加idy.personal==='partner'，或增加idy.partner===true判断
② 统一身份判定口径：个人合伙人应被视为"实名及以上"身份，享有5条/天每日免费额度
③ 建议在deriveIdentity()中增加一个统一的isAuthed()方法，所有Store共用，避免各自实现导致不一致

🟢 问题7（轻微）：CreditStore.expireDue() 60秒节流可能导致余额显示短暂不一致
代码位置：stores.js 第174-194行（expireDue）+ 第206-213行（consume）
核验结论：确认存在，影响极小。expireDue()使用_creditExpireLastRun全局变量实现60秒节流（now - lastRun < 60000时直接return 0）。consume()前调用this.expireDue()（第207行），read()被包裹为每次读取前调用expireDue()（第216行），但两者均受节流限制。极端情况下：积分恰好在上次expireDue执行后的60秒内过期，且用户在这60秒内执行consume()，expireDue直接return不清理，可能允许用户用已过期积分消费。
影响范围：
• 概率极低：需同时满足「上次expireDue执行后60秒内」+「有积分过期」+「用户在此窗口内消费」三个条件
• 仅影响极短时间窗口（最多60秒），下次expireDue执行后会清理
• 不影响数据最终一致性（过期积分最终会被清理）
完整修改建议：
① consume()中的expireDue()调用应绕过节流：增加force参数，consume中调用this.expireDue(true)强制执行清理
② 或在consume()中直接校验：遍历logs检查是否有已过期但未标记expired的入账记录，如有则先扣减再校验balance
③ 可缩短节流间隔至10秒，降低风险窗口（但会增加性能开销）
④ 建议增加单元测试覆盖「积分过期后立即消费」的边界场景
