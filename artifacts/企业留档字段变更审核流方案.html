00背景与问题

当前全站对用户信息的写回遵循"改完即写回 AuthStore + 广播 + toast"的即时模式（编辑器 syncAuthChanges、联系方式页 save()、发票新建抬头）。这套模式对联系方式合理，但对企业身份留档字段存在信任风险。

已坐实的风险点（事实，含行号）：
  • pages/wallet/invoice-title-new.html:120-121：新增企业抬头保存时，无条件执行 auth.enterprise.co = name; auth.enterprise.code = tax; AuthStore.write(auth)，不判断 enterprise.ok。已认证企业可通过"开一张发票抬头"静默改掉企业名称和税号。
  • pages/profile/contact.html:72：联系方式保存时执行 a.enterprise.co = 公司名称。这是一个"联系信息"页，却隐式写了企业名称这个留档字段。
一处与任务背景的事实修正：背景认为"contact.html 不涉及 co/code、无需改动"。但代码中 contact.html 已连通 AuthStore，第 72 行确实写 enterprise.co。因此 contact.html 必须纳入审核流的强制范围（至少对 co 字段）。本方案按代码事实修正，而非按旧认知。

01字段边界定义

把 AuthStore.enterprise 下的字段按"是否构成企业法定身份留档"分为两类。产品判断 分类依据：该字段变更是否影响认证可信度、是否需要营业执照等佐证。

A 类 · 联系信息（即时生效）

可在任意页面直接写回 AuthStore，即时生效 + toast，无需审核。

字段路径
联系人姓名enterprise.contactName
联系电话enterprise.contactPhone
微信号enterprise.contactWechat / personalEntry.profile.basic.wechat
办公地址enterprise.address
所在地区enterprise.region
实名手机realname.mobile

B 类 · 资质留档（已认证需审核）

已认证企业修改时走审核流；未认证企业可直接写回。

字段路径
企业名称enterprise.co
统一社会信用代码enterprise.code
法定代表人enterprise.legal
企业简称enterprise.shortName
命名依据enterprise.nameBasis / nameProof
边界说明：enterprise.address（办公地址）虽在企业实体上，但按任务要求归入 A 类联系信息、即时生效；只有"营业执照注册地址"才属留档，当前 schema 未单独建模，待确认 是否需要拆分"注册地址 vs 办公地址"。

2.2 状态机 产品判断

环节触发系统行为用户可见
触发入口任意页修改 B 类字段且 enterprise.ok=true拦截直接写回，转入申请流程输入框旁"已认证，修改需审核"标识
变更申请用户提交新值写入 pendingChanges（含 reason/files/submittedAt/status=pending）；正式 co/code 不变"变更申请已提交，预计 1-3 个工作日审核"
待审核中—对外仍展示正式值；新值仅存 pendingChanges当前生效值 + 待审核新值并列展示
审核通过审核员操作pendingChanges 值写入正式 co/code；旧值 push 进 changeHistory；清空 pendingChanges；广播 engchain:auth站内通知"企业名称/税号变更已生效"
审核驳回审核员操作清空 pendingChanges，记录 rejectReason；正式值不变站内通知 + 驳回原因"未通过：…"
未认证直改enterprise.ok=false 时修改 B 类字段直接写回正式字段（沿用现状）即时生效 toast

2.3 关键规则 产品判断

  • 单一权威：所有写 B 类字段的入口（发票抬头、联系方式页、企业认证页）必须调用同一个"写企业字段"的守卫函数，禁止各自直接 enterprise.co = ...。
  • 原值冻结：pending 期间，对外展示、撮合、发票抬头均以正式 co/code 为准，pendingChanges 不参与任何业务读取。
  • 并发申请：已有 pendingChanges 未完结时，不允许再次提交；用户可"撤回"（清空 pendingChanges）。
  • 审核主体：复用现有企业认证审核通道（admin 端 auth-review），不新建独立后台。

04UI / UX 要点

输入态标识

  • 已认证企业的企业名称/税号输入框旁显示 已认证 · 修改需审核 徽标。
  • 未认证企业不显示徽标，输入框可直接编辑。

提交后状态

  • 提交后 toast / 状态条："变更申请已提交，预计 1-3 个工作日审核"。
  • 提交表单必含：新值、变更原因（必填）、佐证材料（营业执照照片，必传）。

审核中并列展示

  • 企业认证页同时显示：当前生效值（旧）与 待审核新值（高亮 + 状态"审核中"）。
  • 提供"撤回申请"操作。

结果通知

  • 通过/驳回均发站内通知；驳回必须展示 rejectReason。
  • 个人中心 / 企业认证页展示审核进度与历史变更记录（changeHistory）。

05数据结构扩展建议

在 AuthStore.enterprise 中新增两个字段（向后兼容，旧数据无此两字段时按空处理）：

enterprise: {
  ...原有字段...,
  // 待审核的留档字段变更（已认证企业修改时暂存于此，不覆盖正式值）
  pendingChanges: {
    co: '',            // 新企业名称
    code: '',          // 新统一社会信用代码
    reason: '',       // 变更原因（必填）
    files: [],          // 佐证材料（营业执照照片等）
    submittedAt: 0,    // 提交时间戳
    status: 'none',  // none | pending | approved | rejected
    rejectReason: '' // 驳回原因（status=rejected 时填写）
  },
  // 历史变更记录（审核通过后追加）
  changeHistory: [
    { field: 'co', oldValue: '旧名称', newValue: '新名称',
      changedAt: 0, approvedAt: 0, operator: '' }
  ]
}
兼容性：pendingChanges 缺省为 {status:'none'}，旧版页面读到 undefined 时按"无待审"处理，不影响现有读取。审核通过/驳回后清空 pendingChanges 但保留 changeHistory。

06验收标准

#验收条件验证方式
AC-1已认证企业（enterprise.ok=true）在发票抬头/联系方式页修改 co 或 code → 生成 pendingChanges，正式 co/code 不变改值后读 engchain-auth：正式字段未变、pendingChanges.status=pending
AC-2未认证企业（enterprise.ok=false）修改 co/code → 直接生效同上，正式字段即时更新，无 pendingChanges
AC-3审核通过 → 新值写入正式字段，旧值进入 changeHistory，pendingChanges 清空，触发 engchain:auth模拟审核通过后读数据 + 监听事件
AC-4审核驳回 → 正式值不变，pendingChanges 清空且 rejectReason 有值，用户可见原因模拟驳回后读数据 + 页面展示
AC-5全站所有写 co/code 的入口（invoice-title-new、contact、auth-enterprise）统一走守卫函数，无绕过代码走查：不再出现裸 enterprise.co = / enterprise.code =
AC-6pending 期间，对外展示与撮合仍读正式 co/code，不读 pendingChanges设置 pendingChanges 后打开企业详情/搜索，确认展示旧值
