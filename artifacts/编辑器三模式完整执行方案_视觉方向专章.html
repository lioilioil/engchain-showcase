1任务定义与验收原则

用户目标原文与验收口径，本方案一切设计的判定基准。

1.1 用户目标原文

「按照三种模式考虑：当前的现状的模式、富文本、markdown。新增的富文本模式、markdown 模式，需要充分实现编辑器本身对应的详情页的展示信息以及展示效果的一致性，而不是简单的进行单一输入内容的渲染展示。如果该功能需要 AI 接入，可以考虑；或者通过文本中可以便捷插入组件码的方式来实现。」

1.2 任务边界

  • 范围：编辑器 editor.html 的「详细描述」输入区升级为三模式（纯文本主路径 + 富文本 / Markdown 高级可选）；详情页/详情弹层渲染能力同步升级；数据层兼容三格式。
  • 非范围：9 类业态的动态字段体系、关键参数区、图片/文件上传、付费墙/解锁、列表页卡片视觉改版——保持现状，仅通过渲染管线收口。
  • 已前置完成：聚焦位移 bug（overflow:hidden + scrollIntoView → overflow:clip + 容器内滚动，patch28）；「AI 智能补全」行及其功能逻辑已彻底删除（ai-* 残留 = 0，共享逻辑未破坏）。
  • 交付形态：本文件为完整执行方案（含四角色设计、组件码规范、视觉方向专章、分阶段计划、全栈复核结论），不包含代码修改。

1.3 一致性验收标准（产品级）

  1. 结构一致：同一内容在编辑器预览面板与发布后详情页中，标题层级、列表、表格、引用、代码块的结构完全相同。
  2. 效果一致：字体、颜色、间距、组件卡片的视觉样式一致（同一套 CSS 变量与排版规范）。
  3. 组件一致：文本内插入的组件码，在预览与详情页渲染为同一组件样式。
  4. 摘要一致：列表 / 搜索 / 我的发布中的纯文本摘要，从同一内容提取，无 HTML 残留、无断句错乱。
  5. 兼容一致：历史纯文本数据零迁移成本可读；复制上次发布 / 草稿恢复保持格式不丢失。
核心架构判断：实现「一致性」的唯一可靠方式是单一渲染管线——编辑器预览与详情页调用同一个渲染函数（同一份代码、同一套样式类），而非各自实现一遍。任何「两处各写一套渲染」的方案都必然出现偏差。

3现状基线

改造前的真实代码事实（已核查 editor.html / records.html），所有方案必须建立在这些事实上。

3.1 编辑器现状

  • 「详细描述」为单一大文本框 #f-desc（textarea），placeholder 提示「支持简单的 Markdown 格式」，但实际无任何渲染——纯文本存储。
  • 数据链路：collectData() → description 原样存字符串；草稿 / 自动保存 / 复制上次发布均读写该字段。
  • 主题系统：浅色 / 深色双主题（[data-theme="dark"]）；编辑器作用域主题色「需求=金（默认）、供应=绿」#pub-content[data-role="supply"] 覆写 --primary。
  • 交互约束：已修复的聚焦位移 bug 确立两条铁律——滚动容器显式 overflow:clip；焦点元素用容器内滚动而非 scrollIntoView(center)。三模式编辑器必须继承这两条铁律。

3.2 详情展示现状

  • 发布成功后的详情弹层（editor.html ~2350 行）：'<div …>' + d.description + '</div>' 直接 innerHTML 拼接——纯文本时代无风险，富文本 / Markdown 时代必须接入统一渲染 + 消毒。
  • 列表卡摘要（records.html ~232 行）：esc(r.desc) 转义后纯文本两行截断——是「摘要一致」的现成出口。
  • 搜索关键词：由 title + description 前 80 字截取（editor.html ~2217 行）——富文本 / Markdown 后需从纯文本提取层取词，避免把语法符号当关键词。

3.3 基线结论

  • 三模式改造的唯一侵入点是「详细描述」字段及其渲染出口；其余表单字段（标题 / 品类 / 规格 / 联系人 / 交易要求等）零改动。
  • 渲染出口共三处：详情弹层（富文本渲染）、列表摘要（纯文本提取）、搜索索引（纯文本提取）。三处统一收口到一个渲染模块，即完成「一致性」的数据面闭环。
  • 「AI 智能补全」已删除：确认无 ai-* 残留、共享逻辑（表单校验 / 草稿 / 提交）未被破坏，双角色（demand / supply）回归通过。

4三模式功能设计

三种模式的产品定义：各自做什么、怎么切换、切走切回不丢内容。模式是「视图 + 输入方式」的切换，底层数据始终是同一份结构化内容。v3.1 优先级调整：纯文本 + 组件码 + 实时预览为主路径（默认即用）；富文本 / Markdown 为高级可选（默认隐藏，设置中开启）。

模式输入方式实时预览定位
纯文本
主路径 · 默认		大文本框直接输入逐段成文，格式零损耗（现状行为）最快路径：贴进来就能发，零学习成本
Markdown
高级可选		等宽源码区 + 语法高亮可切换「源码 / 预览」，或双栏并排结构化表达：标题 / 列表 / 表格 / 代码
富文本
高级可选		contenteditable 所见即所得 + 工具栏编辑区下方实时渲染（同管线）零学习成本：选中即加粗，不用记语法

高级可选模式默认不展示入口：在「设置 - 编辑器」中开启后，segment 才扩展为三态。开启与否不影响任何已有发布与草稿——主路径始终可用。

4.1 模式切换

  • 顶部 segment 控件：默认单态（纯文本 + 组件插入按钮）；开启高级模式后扩展为 纯文本 / Markdown / 富文本三态。
  • 切换即时生效，内容一份不丢：纯文本 ↔ Markdown ↔ 富文本互相转换，转换规则由统一中间层（结构化 AST）保证。
  • 切换后光标尽量保持语义位置（按段落近似定位）。
  • v3.1：未开启高级模式的用户不可见 segment，保持现状表单外观，彻底零学习成本。

4.2 工具栏（按模式变化）

  • 纯文本：无工具栏，保留字数统计 + 组件插入入口。
  • Markdown：快捷插入语法（标题 / 加粗 / 列表 / 引用 / 表格 / 代码块）+ 插入组件。
  • 富文本：B / I / H2 / 列表 / 引用 / 表格 / 代码块 + 插入组件 + 清格式。

4.3 实时预览

  • 三模式共用同一个 livepane 预览区，调用统一渲染函数。
  • 富文本模式：编辑区下方实时渲染（压缩编辑区高度保证首屏可见）。
  • Markdown 模式：源码 / 预览切换，预览同样走统一渲染。
  • 组件码在预览中即时渲染为组件卡片。
切换一致性铁律：任何模式下的「所见」（含组件卡、标题层级、表格）在切换后不得走样；切换操作不触发重新输入，只触发「同一内容换视图」。若某格式在目标模式不可表达（如纯文本无表格），降级为可读的标记文本并在预览提示「该结构在纯文本模式以标记展示」。

5统一渲染管线（一致性核心）

「编辑所见 = 详情所呈」的工程实现：一套解析器 + 一套渲染器 + 一套样式，所有出口共用。

5.1 单一渲染函数

新增共享模块 render.js（或 editor.html 内共享作用域），暴露两个纯函数：

renderContent(store) // 输入 {format, content} → 输出安全 HTML
extractText(store)   // 输入 {format, content} → 输出纯文本（摘要 / 搜索用）
  • 编辑器预览 = renderContent(store) 渲染进 .livepane。
  • 详情弹层 = 同一个 renderContent(store) 渲染进详情容器。
  • 列表摘要 / 搜索 = extractText(store) 取纯文本。
统一数据契约 统一渲染管线 所有展示出口共用

5.2 安全设计（XSS 防线）

  • 渲染输出只允许白名单标签（p / h2–h4 / ul ol li / table / blockquote / pre code / strong em / br / a[href 白名单协议]），其余一律转义。
  • renderContent 内部先解析为 AST，再按白名单生成 HTML——绝不直接 innerHTML 用户原文。
  • 链接强制 rel="noopener nofollow" + target="_blank"；图片仅允许组件码内嵌（见第 6 章），正文不渲染任意 img。
  • 现有详情弹层的裸 innerHTML 拼接（editor.html ~2350 行）必须替换为 renderContent() 输出。

6组件码规范

用「一行组件码」把表格、流程、附件、联系方式沉淀为结构化卡片：录入与展示共用同一份数据，编辑器和详情页不再是两张皮。

6.1 四类组件

类型组件码渲染为（编辑器预览 = 详情一致）典型场景
参数表::params 键:值 行「产品参数」两列表格卡规格 / 尺寸 / 材质 / 执行标准
生产步骤::steps 步骤行「生产 / 施工流程」编号时间轴卡工序 / 工期 / 验收节点
文件附件::files 名称+说明「文件资料」附件列表卡资质 / 检测报告 / 图纸清单
联系方式::contact 字段行「联系方式」字段卡联系人 / 电话 / 微信 / 地址

6.2 组件码语法

::params
型号: HM200×200×8×12
材质: Q355B
标准: GB/T 11263

独立成块（前后空行），首行为类型标记，后续行为「键: 值」或步骤行。语法容错：缺值行自动忽略并提示。

6.3 插入交互

  • 编辑器工具栏「插入组件」按钮 → 底部弹出 bottom sheet，四类组件选择。
  • 选择后按当前模式插入：Markdown / 纯文本插入组件码文本；富文本插入一个不可编辑的组件占位块（底层仍是组件码）。
  • 组件卡右下角「编辑」按钮 → 弹窗按字段编辑，保存后回写组件码并重渲染。
一致性红利：组件码使「表格 / 流程 / 附件 / 联系」从正文文本中结构化分离——详情页、列表摘要（组件标题）、搜索索引（组件关键词）全部从同一份组件数据派生，天然一致。

7数据契约与兼容

存储格式、迁移、草稿恢复、搜索摘要的兼容策略——历史数据零迁移是硬约束。

7.1 存储契约

  • 发布记录新增字段：descFormat（'text' | 'md' | 'rich'）+ descRaw（原始内容，按格式存储）+ 保留 description（渲染后纯文本或 HTML，按需）。
  • 兼容规则：descFormat 缺失或 'text' 时，一律按纯文本渲染——历史数据零迁移。
  • 草稿 / 自动保存：同步保存 format，恢复时按原模式打开并还原内容。
  • 复制上次发布：携带 format 还原，格式不丢失。

7.2 摘要与搜索

  • 列表摘要 = extractText({format, content})，先剥离组件码块，再取正文前 N 字——避免把语法符号当摘要。
  • 搜索索引 = 标题 + extractText() 纯文本 + 组件标题（如「产品参数」）。
  • 全部为读取侧派生，不改写存量写入逻辑；存储侧仅加字段，不动表结构。

8前端实现方案

前端开发专家给出的实现路径：DOM 结构、状态机、交互清单、性能与可达性约束。

8.1 DOM 与状态

  • 以「详细描述」卡片为改造单元，内部结构：.mode-seg（默认单态，高级开启后三态）+ .toolbar（按模式渲染）+ .edit-area（textarea / pre / contenteditable 三态）+ .livepane（统一预览）。
  • 状态：mode ∈ {text, md, rich} + store = {format, content} + advancedEnabled（高级模式开关，持久化于设置），切换 = 内容经中间层转换 + 换视图，不丢数据。
  • 富文本用 contenteditable + 防抖 300ms 同步 store；Markdown 用 textarea + 输入即解析。v3.1：首期只实现 Markdown / 富文本的「渲染」能力，编辑器（语法高亮 / contenteditable 工具栏）后置到 P2——渲染管线先行，编辑体验灰度。

8.2 交互清单

  • 模式切换：主路径下 segment 不可见，仅「插入组件」按钮；开启高级模式后 segment 点击即时切换，切换时 toast 轻提示「内容已保留」。
  • 工具栏按钮：Markdown 模式插入语法标记到光标位；富文本模式执行 execCommand（B / I / H2 / 列表 / 引用 / 表格 / 代码块）——均在 P2 落地。
  • 组件插入：bottom sheet 选择 → 插入组件码 / 占位块 → livepane 即时渲染（P1 主路径核心交互）。
  • 字数统计：三模式统一按纯文本计数（含组件块计为结构块），校验逻辑沿用现有 98/5000 规则。

8.3 性能与可达性

  • 渲染防抖：输入停止 200–300ms 后重渲染 livepane；长内容（>2000 字）节流渲染。
  • 继承聚焦铁律：编辑器滚动容器显式 overflow:clip；模式切换 / 工具栏聚焦用容器内滚动定位，禁止 scrollIntoView(center)（patch28 教训）。
  • 键盘可达：segment 可用方向键切换；工具栏按钮有 aria-label；富文本区支持 Tab 插入代码块；焦点环在明暗双主题下均满足 3:1 对比。
  • 动效一律 prefers-reduced-motion 降级（与视觉方向 10.7 一致）。
  • 历史兼容：草稿 / 复制上次发布 / 自动恢复按 descFormat 还原模式与内容。

9后端实现方案

后端开发专家给出的方案：存储、校验、搜索、安全的服务端视角；首期追求「最小后端改动」。

9.1 存储与写入

  • 发布记录增加 descFormat（默认 'text'）与 descRaw（原始内容）；description 字段保留为纯文本摘要（写入时由前端 extractText 结果填充，服务端只做长度校验）。
  • 服务端校验：三格式统一限长（如 5000 字符）；拒绝富文本 / Markdown 原始内容中的脚本标签与危险协议（写入侧白名单校验，纵深防御）。
  • 草稿接口同步携带 format，恢复原样。

9.2 读取与搜索

  • 列表 / 搜索读取 description（纯文本摘要）——现字段零改动即兼容。
  • 详情读取 {descFormat, descRaw} 交给前端统一渲染（渲染必须在客户端完成，服务端不拼 HTML）。
  • 搜索索引：写入侧用 extractText 的纯文本建索引；组件标题（如「产品参数」）作为附加关键词。
结论：后端改动收敛为「两个可空字段 + 写入校验 + 索引派生」，不迁移存量数据、不动表结构、不加中间件。若宿主环境无法加字段，退路是 descFormat 内嵌约定（description 首行注释标记），仍保持零迁移。

10视觉方向（专章）

本版方案的核心增补：由 UI 设计专家牵头，把三模式编辑器的视觉方向单独成章、逐层明确。它既是设计规范，也直接作为实施时的 CSS 变量与组件样式基准。视觉总原则一句话：「蓝图纸上的发布台」——信息像工程图纸一样清晰分层，行动像橙色扳手一样一眼可点。

10.1 视觉母题：蓝图纸 · 工程钢构

编辑器是工程平台的核心录入动作，视觉母题取自工程蓝图与钢结构厂房：

  • 深靛蓝图底是「图纸世界」的底色隐喻——信息区使用克制的蓝灰阶，让内容自己说话。
  • 工程橙只给「该行动」的地方：模式选中态、主操作、语法高亮、组件卡强调——橙色出现即表示「此处可操作 / 此处是关键」。全页面同时只允许一个橙色角色，避免视觉噪音。
  • 等宽字只给机器读的部分：Markdown 源码、组件码、语法标记用等宽字体；正文一律用非等宽正文——「人读的部分」和「机器读的部分」一眼可分。
  • 钢构厂房实景作为预览与详情 hero 的材质锚点（已生图：scene-factory / scene-steel），让平台有工地现场感，而不是通用 SaaS 的玻璃卡片。
  • 发丝线与坐标感：区块分隔用 1px 发丝线 + 克制留白，营造图纸的网格秩序；不做重阴影、不做玻璃拟态。
与现有主题的融合策略：编辑器作用域保留「需求=金、供应=绿」的 --primary 角色变量；本视觉方向的「深靛 / 工程橙」作为编辑器的通用结构色（模式控件、源码区、组件卡骨架），--primary 继续承担表单选中态与主按钮（金 / 绿）。两套色系在编辑器内按「结构 vs 行动」分工，不冲突。此策略已通过 UI demo（390×844 app 原型）与设计评审落地验证。

10.4 模式切换控件（segment）

  • v3.1 默认单态：主路径下「详细描述」卡片保持现状表单外观，无 segment——只有「插入组件」按钮一处新入口；开启高级模式后 segment 才出现，扩展为三态。
  • 形态：胶囊容器内三枚等宽段，容器底 rgba(11,19,34,.06)，选中段工程橙实底 + 白字 + 轻微上浮投影，未选中段透明。
  • 切换动效：选中「滑块」用 180ms ease 位移动画（非整体闪烁）；prefers-reduced-motion 下改为瞬时切换。
  • 每段下可放一行 11px 辅助小字（如「贴文本」「写语法」「所见即所得」），首次使用 3 秒后淡出。
  • 键盘：左右方向键切换，aria-pressed 同步，焦点环在明暗主题均 ≥3:1。

10.5 组件码卡片视觉

  • 卡片骨架：白底 / 深底（跟随主题）圆角 14px，顶部为类型条（图标 + 类型名，如「产品参数」），底部 1px 发丝线分隔操作区。
  • 四类差异：参数表=两列表格；生产步骤=左侧橙色编号圆点 + 时间轴竖线；文件附件=文件名行 + 文件类型小徽标；联系方式=字段行 + 行内可复制按钮。
  • 强调规则：类型条图标用主题色（金/绿），编号圆点与「可点」操作用工程橙——同一卡片内最多两个色相。
  • 编辑态：右下角「编辑」按钮（40px 热区）→ 弹窗表单按字段编辑；悬停 / 按压有 4% 背景变化 + 按压 0.97 缩放。
  • Markdown / 纯文本模式中组件码块以深靛源码底色区分于普通文本，示意「这是结构，不是正文」。

10.6 预览与详情同构视觉

  • 同一套 CSS：预览区与详情弹层共用 .rich-body 样式类（标题层级、列表、表格、引用、代码块、组件卡全部同源）。
  • 详情 hero：详情弹层顶部使用钢构厂房实景（scene-factory）作 16:9 hero，暗场叠加标题信息；预览区首屏同样呈现该 hero 的压缩版，保证「编辑时看到的样子 = 发布后的样子」。
  • 组件卡同构：预览中组件卡即详情中组件卡（同一组件渲染函数 + 同一卡片样式）。
  • 详情弹层的正文容器最大行宽约 40 中文字（保证可读性），预览区同一行宽约束。

10.8 明暗双主题与可达性

  • 浅色主题（默认）：画布 #EEF1F6、卡片白、正文深靛 #16233B；模式控件与源码区用蓝图深靛，工程橙作强调。
  • 深色主题：画布 #0B1322、卡片 #131F36、正文图纸白 #E8EEF9；橙保持 #FF9F43（深底对比 4.5:1 以上），橙色压深版 #E56B2F 用于浅底。
  • 对比度达标线：正文 ≥4.5:1、辅助文字 ≥3:1、橙色作文字 ≥3:1、焦点环 ≥3:1；组件卡与模式控件在双主题下逐项验收（见 10.9）。
  • 非色盲依赖：模式选中态 = 橙底 + 白字 + 粗体三通道（不单靠颜色）；错误 = 红 + 图标 + 文案。

10.9 视觉验收清单

  • 设计令牌已落为 CSS 变量（色板 / 字阶 / 圆角 / 间距），无散落魔法值。
  • 主路径（纯文本 + 组件插入）在 390×844 首屏：编辑区、实时预览、插入入口首帧可见，无 segment。
  • 预览与详情共用 .rich-body 样式类，逐项比对结构 / 效果一致（截图 diff 验收）。
  • 工程橙全页面只有一个角色；「需求金 / 供应绿」仅用于表单行动与选中，无混用。
  • 组件卡四类在双主题下渲染正确，编辑弹窗可回写并重渲染。
  • 开启高级模式后，segment 三态与 Markdown / 富文本编辑区视觉符合 10.3 规范；未开启用户完全无感知。
  • 明暗双主题对比度达标（正文 4.5:1、辅助 3:1、焦点环 3:1）。
  • 动效全部 ≤240ms 且 reduced-motion 降级；聚焦铁律（overflow:clip + 容器内滚动）继承。
  • 列表摘要 / 搜索无语法残留；历史纯文本数据渲染与旧版一致。

11分阶段执行计划

产品经理给出的分期（v3.1 调整）：先打通「一致性管线」，再交付「主路径」（纯文本 + 组件码 + 实时预览），随后灰度「高级模式」（富文本 / Markdown），最后扩展组件库与 AI。每期独立可验收、可回滚。

P0 · 基座
统一渲染管线 + 数据契约
renderContent / extractText 落地；descFormat 字段；详情弹层替换为统一渲染（消灭裸 innerHTML）；历史数据回归。验收：三出口（预览 / 详情 / 摘要）同源一致，安全门全绿。
P1 · 主路径
纯文本 + 组件码 + 实时预览
编辑区下方 livepane 实时预览（默认可见）；四类组件码解析渲染 + bottom sheet 插入 + 卡片编辑回写；列表摘要与搜索索引派生；聚焦铁律继承。验收：主路径双角色回归 + 组件卡在预览 / 详情逐像素一致。
P2 · 高级模式
富文本 / Markdown 渲染 + 可选编辑
渲染能力先行（历史与外部 md/rich 数据可正确展示）；设置开关灰度；Markdown 源码区 + 语法高亮、富文本 contenteditable + 悬浮工具栏；segment 三态。验收：开关关闭时与 P1 完全一致；开启后三模式回归 + 明暗主题截图 diff。
P3 · 扩展
组件库扩展 + AI 可选
交易条款、物流时效等供应场景组件；AI 内容补全（评估后决定是否进入，不阻塞发布）。验收：组件类型可插拔，向后兼容。

11.1 每期出口与回滚

  • 每期结束产出可运行页面 + 双角色回归记录 + 视觉验收截图，交付评审后进入下一期。
  • 回滚策略：渲染管线与格式字段读取侧可降级（descFormat 缺失按纯文本）——任何一期失败都不影响存量发布。
  • 高级模式以开关灰度：关闭状态退回纯文本主路径外观，功能面与现状一致，风险面最小。
  • 编辑器改造全部收敛在 #f-desc 卡片内，其余表单字段零接触，降低回归面。
