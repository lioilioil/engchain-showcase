## 一、任务背景与目标

**背景**：当前 App 的「发布需求 / 发布供应」对**所有已登录 + 已实名用户一刀切开放**，品类只区分 "需求侧 / 供应侧"，没有按用户的**具体身份与认证状态**做能力细分；同时，**企业侧缺少 "我的招聘"**（查看自己发布的岗位、收到的简历、处理投递），招聘业务在企业视角上是断的。

**总目标**（一句话）：让 "谁能发什么" 严格匹配用户身份，让 "发了之后怎么管理" 形成闭环，补齐企业招聘管理能力。

**目标拆解**：



1. 发布能力按 8 类用户画像 × 9 个品类 × 需求 / 供应 双方向，建立明确的**允许矩阵**并落地到代码；

2. 新增 \*\*「我的招聘」\*\* 页（仅企业身份可见），覆盖：我的岗位 → 收到的投递 → 处理投递 → 岗位上下架 的完整闭环；

3. 招聘 / 求职相关的数据模型补齐，投递状态机企业侧可操作；

4. 全部改动经多身份、明暗双主题、全链路回归验证后再交付。

## 三、核心设计：发布能力 × 身份矩阵（目标态）

> 行 = 品类，列 = 用户身份，单元格 = 允许的发布方向（D = 需求侧发布 / S = 供应侧发布 / —= 不可发布 / ✱= 受限专属）



| 品类 \ 身份      | 注册会员         | 个人认证  | 个人专业  | 企业认证  | 入驻・建筑   | 入驻・中介       | 入驻・合伙人 |
| ------------ | ------------ | ----- | ----- | ----- | ------- | ----------- | ------ |
| 材料 / 设备 / 劳务 | D+S          | D+S   | D+S   | D+S   | D+S     | D+S         | D+S    |
| 项目合作         | D+S          | D+S   | D+S   | D+S   | D+S     | D+S         | D+S    |
| 招聘           | —            | —     | —     | **D** | **D**   | —           | —      |
| 求职           | —            | **S** | **S** | —     | —       | —           | **S**  |
| 资质招商         | —            | —     | D+S   | D+S   | D+S     | D+S         | D+S    |
| 建企买卖         | —            | —     | —     | **D** | **D+S** | —           | D      |
| 中介服务         | —            | —     | —     | —     | —       | **S**（仅工作台） | —      |
| 未实名 / 游客     | 全部不可发布（门控引导） |       |       |       |         |             |        |

**设计原则**：



1. **身份即能力**：发布白名单在进入编辑器时按 `entryAccess()` 判定并锁定，品类选择器只出现该身份可用的品类；

2. **企业发招聘、个人发求职**：招聘 = 企业行为（企业认证及以上），求职 = 个人行为（实名及以上），中介企业**不直接发招聘**（引导发「中介服务」帮企业找人）；

3. **建企买卖加严**：收购（D）面向企业认证 + 建筑入驻；转让（S）仅建筑入驻（有资质可售）；

4. **合伙人**：继承个人求职能力 + 建企买卖需求（代买），分销能力保持独立；

5. **门控统一**：游客 / 未实名在任何入口（含 URL 直达）均被编辑器门控拦截。

## 四、迭代计划（分阶段，每阶段目标 + 改动 + 验收）

### 阶段 1：发布门控与品类身份化（解决 P-01/02/03/08）



* **目标**：发布能力按矩阵落地，任何身份进入编辑器只能看到并发布自己可用的品类。

* **改动点**：

1. `editor.html`：`applyCategorySide()` 升级为「身份矩阵白名单」—— 按 `entryAccess()` 身份计算可发布品类集合，隐藏其余品类与快捷填充；非法 URL 参数（如个人带 `cat=招聘`）自动纠正并提示；

2. `publish/index.html` 信息工作台：发布按钮按身份动态化 —— 企业显示「发布招聘 / 发布需求」、个人显示「发布求职 / 发布需求」、中介追加「发布中介服务」；未实名文案细化；

3. `records.html`：「+」入口按身份跳转对应默认方向；

4. `personnel/index.html`：企业端「发布招聘需求」按钮改为**直达编辑器（招聘品类）**，委托弹窗降级为二级入口「委托顾问精准匹配」，文案区分「自助发布」与「人工撮合」两类路径（解决 P-05）；

5. 中介企业发布能力界定落地（矩阵中 "—" 的品类对中介隐藏，如建企买卖 / 招聘）。

* **验收**：8 类画像逐一进入编辑器，所见品类与矩阵完全一致；URL 伪造品类被纠正；明暗主题正常。

### 阶段 2：新增「我的招聘」（解决 P-04/07）



* **目标**：企业身份获得完整招聘管理闭环。

* **新页面**：`pages/profile/my-jobs.html`（我的招聘），仅「企业认证及以上」可见，包含：

1. **岗位列表**：我发布的招聘信息卡（状态：待审核 / 招聘中 / 已暂停 / 已结束），支持上下架、编辑、复制再发；每卡显示「收到简历数 / 未处理数」；

2. **投递管理**：按岗位聚合收到的简历（姓名、证书、期望薪资、投递时间、状态），支持处理：查看详情 → 感兴趣 / 不合适 / 标记已查看；一键联系（展示联系方式或跳转 IM）；

3. **数据看板**：头部统计（招聘中岗位、总收简历、待处理）；

* **入口**（3 处，身份条件化）：

1. 个人中心 `profile/index.html`：企业身份快捷入口新增「我的招聘」；

2. 信息工作台 `publish/index.html`：信息管理区新增「我的招聘」任务卡（带未处理角标）；

3. 人才市场 `personnel/index.html`：企业端头部入口「我的招聘」。

* **验收**：企业发布 1 个岗位 → 个人身份投递 → 企业「我的招聘」看到投递并完成处理流 → 状态同步到人才市场岗位卡片与个人「我的投递」。

### 阶段 3：数据模型与关联补齐（解决 P-06 及状态联动）



* **目标**：投递与岗位、状态机三端联动。

* **改动点**：

1. `js/stores.js`：`ApplyStore` 记录补充 `publisherId`（发布者 uid，按 jobId 反查自动回填）、`jobStatus`（岗位当前状态）；新增 `ApplyStore.listByJob(jobId)` 与 `byPublisher(uid)` 聚合方法；

2. 招聘岗位状态机：`pending_review → active（招聘中）→ paused（已暂停）→ closed（已结束）`，与投递可见性联动（已结束岗位不可再投递）；

3. `my-applies.html`（个人）与 `my-jobs.html`（企业）状态互读，投递处理结果实时回写个人视角。

* **验收**：投递数据三端（个人 / 企业 / 岗位详情）一致；岗位下架后新投递被拦截并有提示。

### 阶段 4：全量交叉检查与验证（专家交叉核对）



* **目标**：交付前系统性回归，防止改一处坏一片。

* **检查清单**：

1. **8 类画像 × 发布矩阵**逐一对账（含 URL 直达、伪造参数）；

2. **明暗双主题**逐页截图核对（editor /my-jobs/records /personnel/publish 工作台 /profile）；

3. **跨身份切换**：u1 发招聘 → u4 投递 → u1 处理 → u4 看结果，全链路走通；

4. **回归**：中介服务锁定（工作台）不受本次影响；服务广场 / 我的单 / 个人中心既有功能正常；

5. **数据一致性**：ApplyStore 旧数据兼容（无 publisherId 的旧投递自动反查补全）。

* **验收**：检查清单全部勾选通过，产出截图证据交付。
