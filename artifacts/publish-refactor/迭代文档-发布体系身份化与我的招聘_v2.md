## 一、任务背景与目标

**总目标**：让 "谁能发什么" 严格匹配用户的**叠加身份**，让 "发了之后怎么管理" 形成闭环，补齐企业招聘管理能力，并让全部改动的 UI / 交互 / 动效有统一规格。

**目标拆解**：



1. 按**叠加身份模型**（账号 = 自然人个人身份 + 可选企业身份）重建发布能力矩阵，纠正 v1 的混淆错误；

2. 「求职」改为**单独核准制**（绑定个人专业入驻，而非实名即得）；

3. 新增「我的招聘」页（仅企业身份侧可见），补齐企业招聘闭环；

4. 数据模型与投递状态机三端联动；

5. 出具本迭代全部页面的 UI/UX/ 交互 / 动效规格并落地；

6. 多身份 × 明暗双主题 × 全链路交叉验证后交付。

## 二、身份模型澄清（v1 核心缺陷修正）

### 2.1 正确的身份模型：账号 = 叠加身份

> v1 把 8 类用户写成 "互斥画像" 是
>
> **错误**
>
> 的。实际模型（
>
> `js/databus.js`
>
>  已实现）：每个
>
> **账号是一个自然人**
>
> ，可叠加
>
> **企业身份**
>
> ：



```
账号（自然人，实名认证）

&#x20;├─ 个人身份 personal：none(未实名) → verified(已实名) → professional(专业入驻，单独核准)

&#x20;└─ 企业身份 enterprise：none → verified(企业认证) → resident(入驻，types∈{construction建筑 / agency中介 / partner合伙人})

（附加标签：dist 分销 / agency 中介 等由 entryAccess 派生）
```



* **u1 陈建国** = 个人 verified + 企业 resident (construction) —— 建筑企业老板，账号同时拥有两侧能力

* **u2 李雅** = 个人 verified + 企业 resident (agency) —— 中介服务商

* **u3 王强** = 个人 verified + 企业 verified —— 认证企业，未入驻

* **u4 张敏** = 个人 professional —— 个人专业入驻（求职者）

* **u5 赵磊** = 个人 verified —— 仅实名

* **u6 刘洋** = 个人 none —— 注册未实名

### 2.2 能力归属原则（核心修正）



1. **能力 = 个人侧能力 ∪ 企业侧能力**，二者按身份分别核算、并存不互斥；

2. **求职 = 个人侧能力，且单独核准**（仅 `professional` 专业入驻获得 —— 需提交个人入驻申请，平台审核通过后方可发布求职，落实 D3）；

3. **招聘 = 企业侧能力**（企业认证及以上即可发布，入驻解锁更高权益如人才库 / 委托）；

4. **中介服务 = 企业侧专属**（仅中介入驻 + 仅服务商工作台进入，保持 v1 已交付锁定不变）；

5. **合伙人（partner）= 叠加标签**，**不单独成行**影响发布矩阵 —— 它继承 "个人或企业叠加结果"，仅额外解锁分销能力（v1 把合伙人当独立画像行，属混淆，已删）。

## 四、发布能力 × 身份矩阵 v2（叠加身份模型）

> 行 = 品类，列 = 身份侧；单元格：D = 需求侧发布 / S = 供应侧发布 / —= 不可发布 / ✱= 受控专属
> **读取方式**
>
> ：某账号可发布能力 = 其 "个人侧行"∪"企业侧行"（若叠加）。

### 4.1 个人侧（按个人身份）



| 品类 \ 个人身份           | 未实名 | 已实名 (verified) | 专业入驻 (professional) |
| ------------------- | --- | -------------- | ------------------- |
| 材料 / 设备 / 劳务 / 项目合作 | —   | D+S            | D+S                 |
| 资质招商                | —   | D              | D                   |
| 求职                  | —   | —              | **S**（单独核准）         |
| 招聘 / 建企买卖 / 中介服务    | —   | —              | —                   |

### 4.2 企业侧（按企业身份）



| 品类 \ 企业身份           | 企业认证 (verified) | 入驻・建筑 (construction) | 入驻・中介 (agency)    |
| ------------------- | --------------- | -------------------- | ----------------- |
| 材料 / 设备 / 劳务 / 项目合作 | D+S             | D+S                  | D+S               |
| 资质招商                | D+S             | D+S                  | **D**（中介不持资质，仅需求） |
| 招聘                  | **D**           | **D**                | —（引导发中介服务）        |
| 建企买卖                | **D**（收购）       | **D+S**（收 + 转让）      | —                 |
| 中介服务                | —               | —                    | **S**（仅服务商工作台）    |

### 4.3 判定速查（示例账号）



| 账号                               | 可发布（并集）                                      |
| -------------------------------- | -------------------------------------------- |
| u1 建筑企业老板（verified+resident）     | 需求 / 供应全品类 (材料设备劳务项目合作资质招商) + 招聘 + 建企买卖收 + 转 |
| u2 中介商（verified+resident agency） | 需求 / 供应 (材料设备劳务项目合作) + 资质招商需求 + 中介服务 (工作台)   |
| u3 认证企业（verified）                | 需求 / 供应 + 资质招商 + 招聘 + 建企买卖收购                 |
| u4 专业个人（professional）            | 需求 / 供应 + 资质招商需求 + 求职                        |
| u5 实名个人（verified）                | 需求 / 供应 + 资质招商需求（**无求职**，需单独核准）              |
| u6 未实名                           | 全部不可发布（门控引导）                                 |

### 4.4 设计原则（修订版）



1. **身份即能力，叠加即并集**：品类白名单 = 个人侧白名单 ∪ 企业侧白名单，按当前账号实时计算；

2. **求职单独核准**：发布「求职」前校验 `professional`（个人专业入驻，平台审核通过）；未核准用户看不到该品类，且提供 "去核准" 引导；

3. **企业发招聘、中介不发招聘**：招聘 = 企业认证及以上；中介定位服务商，发「中介服务」帮企业找人；

4. **中介不持有资质**：资质招商对中介仅开放需求侧（D）；

5. **门控统一**：游客 / 未实名在任何入口（含 URL 直达）均被编辑器门控拦截；

6. **审核兜底**：资质 / 建企买卖等敏感品类发布后走 `pending_review` 平台审核，矩阵只做前置拦截。

## 五、迭代计划（四阶段 + 每阶段 UI/UX 要求）

### 阶段 1：发布门控与品类身份化（P-01/02/03/08/09）

**功能目标**：



1. `editor.html`：`applyCategorySide()` 升级为叠加身份矩阵白名单 —— 按账号实时计算可发布品类，隐藏不可用品类与快捷填充；URL 伪造品类（如个人带 `cat=招聘`）自动纠正并 toast 提示；

2. `publish/index.html` 信息工作台：发布按钮身份化（企业：发布招聘 / 发布需求；专业个人：发布求职 / 发布需求；中介：追加发布中介服务）；

3. `records.html`：「+」按身份跳默认方向；

4. `personnel/index.html`：企业端「发布招聘需求」改为**直达编辑器（招聘品类）**，委托弹窗降级为二级入口「委托顾问精准匹配」并文案区分「自助发布 / 人工撮合」；

5. 求职核准引导：非 `professional` 用户进入求职相关流程时给出 "去个人专业入驻核准" 引导（`auth-prep.html` / `entry-personal`）。

**UI/UX 要求（阶段 1）**：



* 品类区身份化后按可用集合展示；**不可用品类不显示**（不置灰，避免 "看得到用不了" 的挫败感）；

* 若当前身份可用品类 ≥5，保留横向滚动 chips（沿用现有 `.chip` 规范）；≤4 时平铺网格；

* 纠正动作（URL 伪造 / 越权切换）用 toast 提示并自动落回合法品类，不打断填写（沿用现有 `UI.toast` 规范）；

* 工作台发布按钮身份化后，子文案随身份变化（如企业 "发布招聘・招贤纳士"），按钮视觉沿用 `.wb-action` 规范；

* 求职核准引导：采用底部 sheet（沿用 `UI.sheet` 规范），说明核准收益与路径，主按钮去核准、次按钮暂不。

### 阶段 2：新增「我的招聘」页（P-04/07）

**新页面** `pages/profile/my-jobs.html`，仅企业认证及以上可见。

**功能结构**：



1. 头部统计卡：招聘中岗位 / 累计收简历 / 待处理投递（三宫格，风格对齐 `my-applies` 简历卡）；

2. 岗位列表：我发布的招聘信息卡，每卡显示 —— 岗位标题、状态（待审核 / 招聘中 / 已暂停 / 已结束）、收简历数 + 未处理角标；操作：编辑（复用 `editor.html?record=`）、上 / 下架、复制再发；

3. 投递管理（点击岗位展开或二级区）：该岗位收到的简历列表 —— 姓名 / 证书 / 期望薪资 / 投递时间 / 状态；处理操作：查看简历详情（弹层）、标记感兴趣 / 不合适 / 已查看；「感兴趣」后可查看联系方式（脱敏授权）；

4. 空态：未发布岗位 → 引导去发布招聘（直达编辑器 cat = 招聘）。

**UI/UX/ 交互 / 动效规格（阶段 2，重点）**：



* **整体风格**：对齐 `records.html`/`my-applies.html` 的卡片语言（`.card` 背景、`--line` 描边、`--r-m/l` 圆角、CSS 变量主题，明暗自动适配）；

* **状态色规范**：沿用 `--primary`(金) / `--success`(绿) / `--warning`(橙) / `--error`(红) 令牌；岗位状态与投递状态标签复用 `.apply-status` 系样式（`.status-pending/viewed/interested/rejected`），新增 `.status-paused/closed`（灰）；

* **数字角标动效**：未处理数角标在变化时做一次 300ms 弹性放大回缩（`transform: scale(1.25)→1`，`transition` 用 `--e-standard`），不采用持续动画；

* **卡片交互**：按压反馈 `:active { transform: scale(.98) }`；岗位卡可整卡点击进入投递管理，操作按钮不触发整卡跳转（`stopPropagation`）；

* **投递处理流**：查看简历用**底部弹层**（沿用 `UI.sheet`），内容含简历快照（姓名 / 证书 / 经历摘要 / 期望薪资）+ 处理按钮组（感兴趣 / 不合适 / 已查看，主按钮金色渐变、次按钮描边）；点击处理即时回写状态 + toast（"已标记感兴趣，可查看联系方式"），不刷新整页；

* **上 / 下架交互**：切换用**确认弹窗**（沿用 `UI.dialog`：确认 / 取消），说明下架后人才不可再投递；确认后按钮态切换（active↔paused 文案与颜色联动）；

* **空态引导**：大图标 + 两行文案 + 主按钮 "发布招聘"（直达编辑器），沿用 `records.html` 空态规范（`.empty-state/.empty-btn`）；

* **列表过渡**：岗位 / 投递列表渲染用简单 fade-in（`@keyframes` 120ms），不做复杂动画。

**入口（3 处，身份条件化）**：



1. `profile/index.html` 个人中心：企业身份快捷入口新增「我的招聘」（带未处理角标，随 `engchain:apply` 事件刷新）；

2. `publish/index.html` 信息工作台：信息管理区新增「我的招聘」任务卡（带角标）；

3. `personnel/index.html` 人才市场：企业端头部入口「我的招聘」。

### 阶段 3：数据模型与状态机联动（P-06）

## 七、执行价值与风险复查（v2 专项）



| 检查项             | 结论                                                                                    |
