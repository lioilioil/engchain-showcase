服务广场 · 系统内多业务线并行方案

把「服务广场」放进全系统并行视角：与资质招商、建企买卖、人员招聘、综合发现、分销体系六线同台运作时，它的定位、角色边界、资金体系、交叉导流、数据资产与收入模型应如何设计。本方案基于对 D:/Engchain3.0 现有代码与数据层的完整核读，所有金额、比例、档位均取自 js/data.js 单一数据源。

03
角色边界：用户 = 买方，中介 = 合作方，平台 = 规则与资金方 三种身份的价值主张、入口、权限必须各自独立，任何一处混淆都会破坏商业模式

一次办成，不被骗

  • 资金托管 · 里程碑验收 · 未成交退款

合作方 · 中介服务企业

低成本获客，合规经营

资质代办/担保/造价/派遣等持证机构

  • 入驻金V（¥29999 · 破冰期 ¥14999）
  • 工作台上架服务，普通用户不可代发（已拍板）
  • 询盘实时汇聚，意向金锁定成交
  • 里程碑回款 + 佣金透明（仅服务商侧可见）
  • 履约保证金分级（5000/2万/5万）
平台 · 规则与资金方

控制交易闭环，而非信息展示

规则制定 · 资金监管 · 信用治理

  • 撮合 + 审核 + 评级 + 仲裁
  • 意向金与托管账户独立监管
  • 佣金按里程碑释放时扣取（服务商侧）
  • 防跳单规则（聊天封禁/罚款/清退）
  • 数据沉淀 → 远期钻井
红线：「中介服务代表开通了中介服务企业认证」≠ 用户在服务广场替中介发供应。发布「中介服务」品类的权限仅归入驻中介企业；用户侧永远只有「找服务/买服务」的角色。任何让用户进入服务商经营路径的设计都视为错误。
04
交叉导流矩阵：五条业务线如何互相喂养 导流一律走「需求先行」，不做硬导流；每条导流路径都有明确触发场景
资质招商→服务广场
意向加盟者考察后，需资质代办 / 安许代办 / 建造师配置。在招商详情页「下一步需要什么」处，推荐已核验的资质代办服务。需求先行
建企买卖→服务广场
收购方成交后需资质变更 / 人员过户 / 税务筹划 / 银行开户。转让流程「成交后事项」节点挂接企业服务入口。成交后承接
人员招聘→服务广场
长期招不到持证人员的企业，可转向劳务派遣 / 猎头 / 证书挂靠合规咨询服务。招聘空态兜底位给出服务入口。空态导流
企业监控→服务广场
监控到资质到期 / 中标 / 工商变更事件时，按事件类型推荐对应代办服务（如资质延期、安许年检）。事件驱动
服务广场→资质招商 / 建企买卖
代办过程中发现客户有加盟 / 收购 / 转让需求，反向推荐资源线信息。反向导流
综合发现→服务广场
供需流中的「中介」二级 Tab与聚合浏览卡片，全部指向服务广场/详情页；浏览型卡片不承担下单动作。入口统一
口径统一（已确认）：服务广场卡片 = 引导交易（含「在线下单」「资金托管·未成交退款」）；发现页卡片 = 聚合浏览展示。两者是同一条完整信息的不同入口，不是两套卡片体系。

09
风险与治理：并行体系下的五条防线 每条风险都有已落地或待落地的具体机制，防止「多线并行」变成「多线混乱」
跳单（结构性风险）
已有 jumpContract 全规则：警告 → 聊天封禁 7/30 天 → 首罚 ¥5000 → 停业 15 天 → 二次清退。需补充：跳单规则制度条款落到用户协议与保证金规则层。
服务非标 → 客诉
资质代办失败/延期是高频纠纷。已有「超期赔付 / 不过退款」兜底。需补充：平台调解 + 证据链机制（订单消息/进度留痕）。
低频 → 获客贵
一个买方一年仅 1-2 次需求。解法：需求澄清后 AI 长期跟踪 + 服务商主动跟进线索（LeadStore 已支持线索状态流转），拉高 LTV。
身份混淆（已发生的程序缺陷）
历史版本中「中介服务代表」与「入驻中介企业」混淆，导致服务广场无经营入口。已通过入口物理分离（用户侧页 / 个人中心工作台）解决。守则：后续任何页面不得让用户角色代行服务商操作。
刷单 / 虚假供给
需补充：服务商信用分（履约率/响应/纠纷/评价）挂钩流量分配与费率；异常订单风控标记。
资金语义混用
积分 / 诚意金 / 意向金 / 托管 / 保证金文案不得互相借用。守则：每个资金名词在全局唯一、页面口径一致（数据层已是单一数据源）。
