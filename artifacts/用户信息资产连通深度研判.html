00结论先行

全站已经存在一个事实层面的权威源 AuthStore（js/stores.js:63，localStorage engchain-auth），并具备成熟的回写广播机制：AuthStore.write() 自动派发 CustomEvent('engchain:auth')，约 30 个页面已监听并随身份刷新。编辑器（publish/editor.html）已经跑通了"读取预填 → 认证标识 → 修改回写 → 广播 → 用户可见 toast"的完整闭环，这是全站唯一的样板。

但这套机制只覆盖了约 1/3 的用户信息触点。其余触点分三类问题：(1) 独立 localStorage 各存一份（发票抬头、银行卡、个人资料、城市）；(2) 两个本应是"联系方式主入口"的页面（contact / security）完全是硬编码 mock，既不读也不写；(3) 匹配偏好没有从用户已认证的地域/资质自动取默认值。结果就是同一套"姓名/手机/微信/公司/地址/税号"在编辑器、发票、银行卡、联系人页被反复要求填写或互相不一致。

3.4 静默同步缺失 / 纯 mock 断点 事实

contact.html 是最严重的断点：它在导航上叫"联系方式"，本应是用户修改手机/微信/公司/地址的唯一编辑入口。但当前实现（contact.html:28-31）四个字段全部是 value="138****8866" 等硬编码，save()（:43）只弹 toast 就 history.back，没有任何 AuthStore.read / write。用户在这里改了手机号，界面看似保存成功，实际什么都没发生——这是静默失败。
security.html 同类问题：登录手机号 138****8866（:29）、"已设置/已绑定"（:30-31）全是静态文案，不读 realname.mobile。用户在实名认证后改了手机号，这里仍显示旧掩码。

对比之下，编辑器的同步是有可见反馈的（toast"已同步至企业入驻信息"）。改造时必须把"写回 → 广播 → toast"三件套作为硬要求，杜绝静默。

4.2 读取规范 / 回写规范 产品判断

读取规范

  • 任何展示用户身份信息的页面，不得在 HTML 里写死 value="..."；必须 AuthStore.read() 后填充。
  • 预填遵循编辑器范式：仅当字段为空才填（prefill 不覆盖用户已填内容）。
  • 掩码规则统一用 realname.idMask / 姓名掩码函数，不在各页各写一套。
  • 已认证字段旁加统一的 auth-badge「已认证」标识，未认证引导去认证。

回写规范（三件套）

  • 修改提交 → AuthStore.write(next)（自动持久化）。
  • 确认广播：window.dispatchEvent(new CustomEvent('engchain:auth'))（与 editor.html:1452 一致）。
  • 用户可见反馈：UI.toast('已同步至…', 'ok')，禁止静默保存。
  • 监听侧：需要随身份刷新的页面补 window.addEventListener('engchain:auth', render)。

4.4 冲突处理：编辑器联系方式 vs 企业入驻信息 产品判断

现有 syncAuthChanges（editor.html:1426）检测到 5 个联系人字段变更后，会直接把编辑器里的值写回 enterprise.contactName/contactPhone/contactWechat。推断 这是为了"发布者对外展示的联系方式"与"企业认证留档联系方式"保持一致。

风险：enterprise.contact* 是认证留档字段，编辑器是对外展示上下文。如果允许编辑器静默覆盖已认证的留档电话，可能出现"对外展示号 ≠ 认证备案号"的合规风险。产品建议：
  • 未认证状态（enterprise.ok=false）：编辑器修改直接写回，无冲突。
  • 已认证状态（enterprise.ok=true）：编辑器修改联系方式时，不直接覆盖认证字段；改为提示"企业认证留档电话为 …，如需变更请前往企业认证重新提交审核"，或在编辑器内发起"变更申请"并把 enterprise.contact* 标记为 pending_review，审核通过前对外仍展示旧值。
  • 个人联系方式（realname.mobile / profile.basic.wechat）属个人资产，可直接写回，无需审核。

5.3 连通后匹配口径的具体受益 推断（需上线后用数据验证）

  • 降低冷启动：match 偏好的"关注地区"不再默认"不限"，而是用户已认证所在地，新用户首次进入即有合理推荐，不必从零勾选。
  • 提高匹配精度：撮合从"用户自填的经营范围"升级为"营业执照/资质证书审核后的字段"，减少虚报与空填。
  • 降低操作门槛：同一套联系方式在发布、开票、提现、被联系时自动一致，用户只需在一个地方维护。
  • 提高对接转化：联系人字段来自已认证企业，解锁后即拨即达，减少"留了号打不通"的流失。
待验证 以上收益为基于数据一致性逻辑的推断，具体提升幅度需在连通改造后用 A/B 或前后对比验证（如：首次推荐有效率、联系方式拨打接通率、发布页填写完成率）。报告不承诺具体数字。
