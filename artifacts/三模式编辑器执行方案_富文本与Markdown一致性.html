发布编辑器三模式执行方案
纯文本 / 富文本 / Markdown 与详情页展示一致性

针对 pages/publish/editor.html（发布需求 / 发布供应双角色）的"详细描述"区域，设计三模式编辑能力，核心目标是编辑器预览与详情页渲染的展示信息、展示效果完全一致；通过统一渲染管线 + 文本组件码机制实现，AI 作为可选增强路径。
编制角色：产品经理 · 前端开发专家 · 后端开发专家 · UI 设计专家 复核角色：全栈开发专家 日期：2026-09-22

1任务定义与验收原则

用户目标原文："按照三种模式考虑：当前现状的模式、富文本、markdown。新增的富文本模式、markdown 模式，需要充分实现编辑器本身对应的详情页的展示信息以及展示效果的一致性，而不是简单的进行单一输入内容的渲染展示。如果该功能需要 AI 接入，可以考虑；或者通过文本中可以便捷插入组件码的方式来实现。"

1.1 任务边界

  • 范围：编辑器 editor.html 的"详细描述"输入区域升级为三模式；详情页渲染能力同步升级；数据层兼容三格式。
  • 非范围：9 类业态的动态字段体系（kvlist/taglist/steplist 等）、关键参数区、图片/文件上传、付费墙/解锁、列表页卡片视觉改版——均保持现状，仅通过渲染管线收口。
  • 交付形态：本文件为执行方案（含四角色设计、组件码规范、分阶段执行计划、全栈复核结论），不包含代码修改。

1.2 一致性验收标准（产品级）

  1. 结构一致：同一内容，在编辑器预览面板与发布后详情页中，标题层级、列表、表格、引用、代码块的结构完全相同。
  2. 效果一致：字体、颜色、间距、组件卡片的视觉样式一致（同一 CSS 变量与排版规范）。
  3. 组件一致：文本内插入的组件码，在预览与详情页渲染为同一组件样式。
  4. 摘要一致：列表/搜索/我的发布中的纯文本摘要，从同一内容提取，无 HTML 残留、无断句错乱。
  5. 兼容一致：历史纯文本数据零迁移成本可读，复制上次发布 / 草稿恢复保持格式不丢失。
核心架构判断：实现"一致性"的唯一可靠方式是单一渲染管线——编辑器预览与详情页调用同一个渲染函数（同一份代码、同一套样式类），而非各自实现一遍。任何"两处各写一套渲染"的方案都必然出现偏差。

3产品经理设计：三模式定义与产品逻辑

产品层回答三个问题：三种模式分别服务什么用户与场景、模式之间如何切换与互转、什么机制保证"编辑所见 = 发布所得"。

3.1 三模式定义（产品口径）

模式适用场景交互形态存储格式
模式A纯文本 简单供需（一句话/短描述）、快速发布、低学习成本用户 现有 textarea 不变，无工具栏，保持轻量 format=plain，纯文本
模式BMarkdown 工程类长描述（项目概况/技术要求/工期条款/资质要求等结构化内容）、习惯源码编辑的用户 源码编辑 + 实时预览分栏；工具栏提供标题/列表/表格/引用/组件快捷插入（生成语法） format=md，Markdown 源文本
模式C富文本 希望所见即所得、从 Word/微信复制粘贴长内容的用户（建筑行业乙方常见） 轻量富文本编辑器（工具栏：加粗/斜体/标题/列表/引用/表格/图片/组件）；粘贴自动清洗 format=rich，白名单 HTML

3.2 模式切换与互转

  • 入口：描述区顶部"内容格式"segmented 三段切换（纯文本 / Markdown / 富文本），与现有"详细描述"标题同排。
  • 切换保留内容：切换时执行无损互转——
    • plain → md：文本按空行分段（不引入额外语法），保真。
    • md → plain：strip 为纯文本（去掉语法标记）。
    • md → rich：renderContent(md) 生成 HTML 载入富文本编辑器。
    • rich → md：富文本内容序列化为 Markdown（自研轻量 serializer，覆盖白名单子集）。
  • 用户偏好记忆：记住用户上次选择的模式（localStorage），下次默认进入。
  • 模式与业态不绑定：9 类业态均可使用任意模式；不做"品类强绑定"，避免过度约束。

3.3 一致性产品逻辑

  • 预览即详情：编辑器右上"预览"按钮打开的面板，其描述区域渲染逻辑与详情页完全同源（同一渲染函数 + 同一 CSS）。产品验收点：在预览面板截图与详情页截图做像素对比。
  • 格式不降级：发布、存草稿、复制上次发布、编辑历史中，contentFormat 全程保留，不因中间环节丢失。
  • 历史数据：老数据视为 plain，正常展示，无迁移提示、无升级门槛。

3.4 组件码机制（产品口径）

目标：用户能在描述正文任意位置插入结构化组件，详情页渲染为与现有动态字段区块同风格的卡片。区别于现有动态字段（表单内独立区块），组件码是文本流内的结构化片段，表达力更强（可插在上下文中间）。

组件用途示例编辑交互
params 参数表"关键参数：材质 Q355B / 厚度 16mm / 屈服强度 355MPa"插入向导：键值对表单 → 生成组件码
table 通用表格工期节点表、验收标准表向导：行列数 + 单元格编辑
steps 流程步骤"交易流程：对接→审核→合同→进场→结算"向导：步骤列表（复用 steplist 视觉）
files 文件清单"资质文件：质检报告 / 合格证"向导：文件名清单（详情页展示文件块）
contact 联系人卡片正文中插入对接人信息卡向导：姓名/职务/电话
产品决策：v1 组件仅 5 种，全部为纯结构组件（不承载脚本、不承载可执行内容），组件码语法统一、可手写、可删除、可批量替换。图片墙/文件上传等沿用现有表单能力，不引入文本内嵌。

3.5 AI 接入（产品口径 · 可选增强）

AI 能力产品价值
① 文本 → Markdown/富文本 格式化用户粘贴长文本，一键整理为结构化的 Markdown（标题/列表/表格），降低学习成本
② 文本 → 组件码 智能识别识别描述中的参数、流程、资质清单，生成对应组件码插入正文
③ 一致性体检提交前检查组件码/表格语法完整性，提示修复

定位：AI 是生产力增强，非必需依赖——三模式与组件码全链路离线可用；AI 仅在用户主动点击"AI 整理"时介入。接入方式见 7.4。

4前端开发专家设计：统一渲染管线与编辑器实现

前端层回答：如何用一个渲染函数同时服务编辑器预览与详情页；三模式编辑器各自怎么实现；组件码如何解析与安全渲染。

4.1 核心架构：统一内容渲染管线

渲染管线（唯一实现） 组件码注入路径 Markdown 输入 富文本输入
  • 新文件：js/content-render.js（无依赖、ES5、约 400 行），包含：renderContent(content, format)、renderMarkdownV2()（升级：表格/代码块/图片/组件码/嵌套列表）、sanitizeRich(html)（DOMParser 白名单）、stripToText(content, format)（摘要用）、serializeRichToMd(html)（互转用）。
  • 接线：editor.html 与详情页（detail.js 所在页面）均引入 content-render.js；detail.js 中 .ds-text 路径替换为 renderContent(rec.description, rec.contentFormat || 'plain')；.md-content 路径同步收口（descMd 历史字段并入统一路径）。
  • 降级：content-render.js 加载失败时，detail.js 回退到现有纯文本渲染（不白屏）；预览面板回退到现状。

4.2 编辑器三模式实现方案

模式 A 纯文本

保持 f-desc textarea 不动，仅修正 placeholder 文案（去掉"支持简单的Markdown格式"误导），改为"补充项目概况、要求、工期、资质等信息"。渲染走 renderContent(plain)（转义 + 空行分段）。

模式 B Markdown

  • 容器：textarea（源码）+ 顶栏工具条（标题 H1/H2/H3、粗体、斜体、列表、有序列表、引用、表格、链接、插入组件）——点击在光标处插入对应语法。
  • 预览：源码区下方/右侧"预览"分栏（移动端切换式），实时调用 renderContent(md)，300ms 防抖。
  • 表格输入：工具栏"表格"打开 3×3 栅格选择器 → 生成 | 表头 | ... | 语法块。

模式 C 富文本（关键技术决策）

前端决策点：项目为移动端优先的离线单文件 H5（无构建链、无框架），原生 contenteditable 在 iOS/Android WebView 上存在光标漂移、工具栏失焦、execCommand 兼容性等系列问题。推荐方案：不直接使用 contenteditable 做主力编辑，采用"标记化富文本"策略——底层仍是带轻量语法（**粗体** / ## 标题 / - 列表 / | 表格 |）的文本编辑，工具栏按钮在光标处注入语法标记并实时预览，视觉上呈现富文本效果；该策略与 Markdown 模式共享渲染器，互转零成本，且彻底规避移动端 contenteditable 风险。

方案对比（给决策留档）：

方案优点缺点/风险
方案 C1：标记化富文本（推荐）移动端零风险、与 md 互转零成本、离线自包含、实现量小（≈300 行）粘贴 Word 富文本需清洗转语法；不是"真 WYSIWYG"（预览与输入分离）
方案 C2：contenteditable 自研真所见即所得移动端光标/键盘/工具栏坑多；execCommand 已废弃；需大量兼容处理（高风险、高成本）
方案 C3：第三方库（wangEditor/Tiptap CDN）功能完整引入 CDN 依赖（项目当前零依赖）；体积大；定制风格成本；离线不可用

建议：v1 采用 C1（标记化富文本，编辑器内始终"语法 + 实时预览"双轨，体验接近富文本）；若后续桌面端/Web 端形态出现且有构建能力，再评估 C2/C3 升级。C1 的存储格式仍为 format=rich？——否：C1 实际存储与 md 相同语法，为避免语义混乱，统一将 C1 的输出按 format=md 存储，"富文本"作为编辑交互形态存在（产品层面仍是三种模式，技术层 md 与 rich 共用一个渲染内核；若未来引入 C3，rich 才独立存储 HTML）。此决策大幅简化数据层与渲染层。

粘贴清洗

粘贴 Word/微信内容时（模式 B/C），读取 clipboardData 的 text/html 与 text/plain：HTML 存在时经 DOMParser 提取结构（标题/段落/列表/表格），转换为 Markdown 语法（复用并重写原 aiCleanText 思路，产出为安全 md 而非 HTML）；纯文本直接按空行分段。

4.3 组件码机制（技术规格）

语法（Markdown 友好、可手写）

:::cmp params
材质: Q355B
厚度: 16mm
屈服强度: 355MPa
:::

或单行紧凑形式（表格/步骤场景）：

:::cmp steps|交易流程
1. 需求对接
2. 资质审核
3. 合同签订
:::
  • 解析：renderContent 内部用正则扫描 :::cmp\s+(\w+)(?:\|([^\n]+))?\n([\s\S]*?)\n:::，按类型调用组件渲染器（白名单类型表：params/table/steps/files/contact），输出带 class="content-cmp content-cmp-类型" 的静态结构。
  • 未识别类型：降级为 :::cmp 原样文本（不隐藏、不报错），保证数据可逆。
  • 安全：组件内容一律纯文本取值 + 转义输出；不解析任何 HTML/JS；键值对以"第一个冒号"切分。
  • 样式：组件视觉复用详情页现有区块风格（边框卡片、键名灰、键值深色），保证与动态字段区块同语言。

编辑器内插入向导

工具栏"插入组件"→ 半屏 sheet（类型选择 + 简易表单）→ 生成组件码插入光标处。Markdown 模式下即普通文本插入；富文本（C1）模式下同样插入语法块。
